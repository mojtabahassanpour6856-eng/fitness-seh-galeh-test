# بازبینی migration کاندید بازیابی رمز بدون پیامک

این migration صرفاً فایل پیشنهادی است و روی Supabase اجرا نشده است.

## تغییرات پیشنهادی
- افزودن `code_envelope text` برای envelope رمزگذاری‌شده AES-256-GCM.
- تغییر قید `token_attempts` از سقف ۱۰ به سقف ۵.
- RPC اتمیک ثبت تلاش ناموفق؛ تلاش پنجم وضعیت را expired می‌کند و verifier/envelope/expiry را پاک می‌کند.
- RPC اتمیک claim کد صحیح؛ فقط یک درخواست هم‌زمان می‌تواند approved را به processing ببرد.
- دسترسی اجرای RPCها فقط برای service_role.

## ملاحظات امنیتی و محدودیت‌ها
- این RPCها فقط مکانیزم اتمیک دیتابیس‌اند؛ احراز هویت JWT شاگرد، تطبیق auth_user_id، کنترل مالکیت مربی و محدودیت نرخ باید در Edge Function انجام شود.
- `p_expected_verifier` باید HMAC تولیدشده با pepper سرور باشد؛ هرگز کد چهاررقمی یا SHA-256 ساده ارسال نشود.
- برای تلاش ناموفق، Edge Function باید فقط وقتی verifier ذخیره‌شده موجود و درخواست approved و منقضی‌نشده است RPC را فراخوانی کند.
- مسیر claim صحیح باید پس از بررسی ثابت‌زمانی/مقایسه امن verifier انجام شود؛ در صورت شکست Auth باید recovery امن و idempotent جداگانه طراحی شود. برگرداندن processing به approved بدون تعیین تکلیف نتیجه تغییر رمز خطرناک است.
- migration قید قبلی را با نامی که در schema مشاهده شد جایگزین می‌کند؛ قبل از اجرا باید وجود قید، وابستگی‌ها و داده‌های موجود با snapshot تازه بررسی شوند.
- این migration هنوز expiry بیست‌وچهارساعته، صدور کد، HMAC، AES-GCM، cleanup پس از موفقیت و rate limit را پیاده‌سازی نمی‌کند؛ آن‌ها مسئولیت Edge Function و secrets هستند.
- تغییر سقف تلاش ممکن است با داده‌های موجودی که token_attempts بالاتر از ۵ دارند ناسازگار باشد؛ پیش از اجرای واقعی باید تعداد/وضعیت این ردیف‌ها فقط با SELECT بررسی و برایشان تصمیم migration گرفته شود.

## آزمون‌های لازم پیش از اجرا
1. دو claim هم‌زمان با verifier درست: دقیقاً یکی true.
2. تلاش‌های ناموفق موازی: شمارنده هرگز بالاتر از ۵ نرود و تلاش پنجم expired کند.
3. verifier نادرست یا request_id نامرتبط: هیچ ردیفی تغییر نکند.
4. وضعیت غیر approved و expiry گذشته: claim و attempt هر دو بی‌اثر باشند.
5. نقش anon/authenticated نتواند RPC را اجرا کند؛ service_role بتواند.
6. rollback و اجرای مجدد migration روی دیتابیس ساختگی/موقت.
7. تست بازیابی پس از timeout مبهم Auth قبل از هر اتصال به endpoint واقعی.
